Agent Engineering & AI SDLC
1. Bug blindness (the human-side quality ceiling)
MomentumHigh SentimentPositive Production ReadyHigh Hype RiskLow ConfidenceHigh
What is happening

Dan Luu's "Bug blindness" (HN 269 pts / 159 comments) names the failure of humans to notice software defects they are habituated to compensating for, once those compensations go subconscious — the mechanical-mouse-ball story, the Google-Docs title-typing habit, the Codex escape-key timing. German has a word for it: Betriebsblindheit. Corroborated in-thread by named engineers (Gary Bernhardt, Michael Malis) and a Codex-specific compensating-habit comment.

Why it matters

This is the perception-side complement to the deterministic-gating / verification-debt stack. LLMs make quality improvement cheaper than ever, "but to do this, you have to actually notice that this is possible." Dogfooding cannot break bug blindness because dogfooders carry the same compensating habits. Reframes agentic code review as partly a perception-training problem: an LLM simulating a naive user can reproduce defects across scenarios that the habituated team no longer sees.

Evidence from real teams

Luu cites shipping teams whose products "fell flat on its face because users run into the exact same issues I saw" — i.e., the blindness was always there; LLM-user simulation now makes it externally reproducible. The Discourse LCP-cheating and Blackboard-employee-who-thought-it-was-loved cases are the historical data points.

Engineering implication

Add "LLM-as-naive-user" reproduction to the verification pipeline — it surfaces defects the team's habitual mitigations mask. Pair with deterministic gating and the verifier-first loop. Verdict: Adopt as a perception-side check; it costs almost nothing and targets a failure mode no other control covers.

2. Domain-Driven Agents (the input-readiness layer)
MomentumMedium SentimentPositive Production ReadyMedium Hype RiskLow ConfidenceMedium
What is happening

Ernest Bednarczyk's "Domain-Driven Agents" (Aug 27) applies DDD (bounded contexts, ubiquitous language, context maps) as the prerequisite input that makes LLM agents viable in brownfield codebases. The failure has a specific shape: the model invents a fourth spelling of a concept that already exists three times because the codebase never decided which was real. Operationalized via a .workflow.json manifest + per-context CONTEXT.md glossary + a derived, machine-checkable context map that auto-files DDD issues with fingerprints.

Why it matters

This is the missing strategic half of harness engineering. Harness engineering optimizes the runtime wrapper; context engineering optimizes the prompt window; DDD-as-readiness optimizes the system the agent reads. It reframes the economics: the mechanical half of tech-debt cleanup collapsed in cost (LLM does the typing), but the deciding half — which concept is real, where a context ends — stayed expensive and is exactly what the agent needs encoded.

Evidence from real teams

Single-author working repo (job-offer-box, Rust backend + web frontend). Not yet multi-team corroboration, but the mechanism (machine-checkable context map, auto-filed DDD issues with fingerprints, closed-loop issue→agent→PR→review spine) is concrete and reproducible.

Engineering implication

For brownfield agent rollout, invest in ubiquitous-language/context-map artifacts before tuning the harness — the model guesses wrong less when the system answers its questions. Verdict: Trial on a brownfield repo; the mechanism is low-cost and targets the actual failure mode.

3. Harness engineering — construction→evaluation inflection holding
MomentumExplosive SentimentPositive Production ReadyHigh Hype RiskMedium ConfidenceHigh
What is happening

Now 25+ sightings (first seen 2026-08-02) and still the dominant enterprise economics story, productized at three layers (DeepSeek Harness MIT, Databricks Omnigent meta-harness, NVIDIA NeMo Switchyard router). This run's reinforcement: harness-config defaults — not model weights — remain the binding production lever. GLM-5.3's reasoning_effort=max default and Qwen 3.8-27B's xhigh default both trigger pathological overthinking (30+ min on a trivial port, zero code); a one-line config fix (fixed chat templates + thinking=low) lifted completion 62%→92%.

Why it matters

The field's binding open problem has decisively shifted from harness-construction to harness-evaluation (cost-per-successful-task at a held-out quality bar). Terminal-Bench-Science (Aug 27), NanoGPT Speedrun Frontier, and Artificial Analysis Optima are the operationalized answers — all turn "build your own benchmark" from advice into executable tooling.

Evidence from real teams

Decagon running ~90% of agents on fine-tuned open-source models (driven by latency/accuracy, not cost); Ramp, LangChain, CrowdStrike, Harvey on NeMo Switchyard routing; Anthropic's own Applied AI team publicly states harnesses — not models — are the limiting factor.

Engineering implication

Own your harness config as a versioned, reviewed artifact; pin reasoning_effort by workload. Build a private held-out eval before trusting any leaderboard. Verdict: Adopt.
